### What it is

The one thing a language model cannot do by itself is find out whether its answer works. It
writes a function and stops. The organism writes a function, RUNS it, reads the failure, and
writes another one. That loop is the whole claim of this board, and `bench/code.mjs` is the
measurement of it against the same model doing the same job with one look and no run.

| file | what it is |
| --- | --- |
| `act/run.mjs` | the sandbox: `runCases(code, cases, opts)`, `renderValue`, `sameValue` |
| `act/code.mjs` | the loop: `solveCode(task, opts)`, `firstPrompt`, `repairPrompt`, `extractCode`, `entryName` |
| `bench/code.mjs` | the bench, the seeded task generator and the reference implementations |
| `bench/fixtures/code-tasks.json` | 40 tasks, 120 visible cases and 160 hidden ones |
| `test/code.test.mjs` | 15 tests over the sandbox, the loop and the fixture |

### The sandbox contract, in words

A candidate is a string. It never becomes a file, it is never imported, and it never runs in
the process that is grading it. `runCases` puts it behind two walls.

**The worker.** Every candidate runs inside a `worker_threads` Worker with `resourceLimits`
(`maxOldGenerationSizeMb` at the caller's `memoryMB`, 128 by default), so a candidate that
allocates without bound dies in its own heap. Each case carries a wall clock limit, 2000 ms
by default, and that limit is enforced by `worker.terminate()` from the parent, because a
synchronous infinite loop cannot be interrupted from inside the thread running it and
cannot answer a message asking it to stop. A case that hits the deadline costs the worker:
it is terminated, the case is recorded failed with the elapsed time and the reason, and the
next case starts a fresh worker. A candidate that wedged a thread has also wedged whatever
state it left behind, so that state is not carried forward.

**The context.** Inside the worker the candidate is compiled into a `node:vm` context whose
global has been pruned to exactly `Math`, `JSON`, `Array`, `Map`, `Set`, `String`, `Number`,
`Boolean`, `BigInt`, `RegExp`, `Object`, `Symbol` and `Error`, plus the candidate itself.
There is no `process`, no `require`, no `import`, no `fetch`, no `WebAssembly`, no
`Atomics`, no `SharedArrayBuffer`, no timer, no `console`, no `Promise` and no `Date`, and
the context is created with `codeGeneration: { strings: false, wasm: false }`, so `eval` and
the `Function` constructor throw instead of reaching an intrinsic the prune could not
delete. A candidate that reaches for the filesystem or the network gets a `ReferenceError`,
and that `ReferenceError` is recorded as that case's failure, not as an error in the bench.
The sandbox itself opens no socket and touches no file.

**One comparison rule for both sides.** `renderValue()` maps a value to a JSON value: a
BigInt becomes its decimal string, `-0` becomes `0`, `NaN` and the infinities become their
names, `undefined` becomes `@undefined`, and object keys are sorted. The expected value from
the fixture and the value the candidate returned go through the same function before they
are compared, which is what lets a candidate returning
`123456789012345678901234567890n` match a fixture that can only hold that number as a
string. Expected values are JSON values; a `Map` or a `Set` renders only as far as JSON can
carry it, and nothing in the fixture expects one.

### The task kinds, and the counts

`bench/fixtures/code-tasks.json` holds 40 tasks at seed `code-2026-09-18`: 120 visible cases
the model is shown and 160 hidden cases no prompt ever carries. Thirty are generated by the
seeded generator in `bench/code.mjs` and their expected values come from the reference
implementations in that same file, running in full Node; each task records
`expectedFrom: "a reference implementation in bench/code.mjs"`. The kinds were chosen
because the candidate runs with almost none of Node and the reference runs with all of it:

| kind | tasks | what a small model gets wrong |
| --- | --- | --- |
| `bigint` | 6 | mulAdd, powMod, fib, factorial digit sum, binomial, gcd: the answer does not fit a double, so `Number` arithmetic is silently wrong |
| `string` | 6 | reverse, toggle case, run length, count, collapse, length: over the empty string and over characters outside the basic plane, where one character is two code units |
| `array` | 6 | rotate, kth largest, longest run, window sums, lower bound, drop every nth: one indexed positions, windows, and the first element at or above a value |
| `date` | 6 | days between, day of year, weekday, add days, is leap, end of month: there is no `Date` in the sandbox, and 1900 and 2100 are divisible by four and are not leap years |
| `parser` | 6 | one expression evaluator: precedence, parentheses, unary minus, and division that truncates toward zero, with no `eval` |
| `hand` | 10 | count letter, sum to n, palindrome, fizzbuzz, median, roman numerals, title case, balanced brackets, binary gap, digit sum |

The ten hand tasks carry `expectedFrom: "typed by hand into this fixture"`: their 70 expected
values were written out, not computed. Before the fixture was committed, ten independently
written correct solutions were run through the sandbox against all 70 of those cases and all
70 passed, and twelve independently written solutions were run against the generated tasks of
every kind and all 84 of their cases passed; neither of those runs is the bench and neither
is in the verdict, but a fixture whose answers no correct program can reproduce would have
measured nothing.

`--regenerate` rewrites the fixture from the seed. The generator is deterministic, and
`test/code.test.mjs` asserts every task of the committed file against a fresh build at that
seed, with a different seed as the control so that the equality is the seed doing the work.

### The loop

`solveCode(task, { provider, rounds })`. Round 1 is the spec, the signature and the visible
examples. The candidate is extracted from the last fenced block the model wrote and run on
the visible cases. On a failure, the failing case goes back with the candidate that produced
it (the call, and either what it returned against what it should have returned, or the error
it threw), and the model is asked again, up to `rounds`, 3 by default. The FIRST candidate
that passes every visible case is the one graded on the hidden cases; when no candidate
passes them all, the LAST one is graded, so an arm always has a number and the number is
never chosen by looking at the hidden cases. The ledger event `act.code.solve` records the
rounds spent and the candidate count, never the prompt and never the code.

`provider: 'null'` is the floor and not a model that failed: no prompt is built, no socket is
opened, and the candidate is a function that returns `undefined`, graded by the same runner
on the same hidden cases. Its result carries `rounds: 0`, and the test asserts that against
`probedBases()` from `act/llm.mjs`, which records every base a socket was opened to.

### The three arms

Interleaved TASK BY TASK, never arm by arm: all three arms answer task i before any arm sees
task i+1, and the first arm rotates with i.

- **organism**, `solveCode` with `rounds: 3`, then the hidden cases.
- **alone**, the identical first prompt, ONE model call, no run and no repair, graded on the
  same hidden cases by the same runner. The two model arms differ in the loop and in nothing
  else: same model, same prompt, same extraction, same sandbox.
- **null**, no model and no socket.

One ruler: a task counts when EVERY hidden case passes. The share of hidden cases passed is
reported beside it as the generous edge and decides nothing, because a function that gets
three of four cases right is a function that does not work.

Two things are written rather than promised. An arm that could not reach the model is
`absent` with the reason and its accuracy is `null`, never zero, because zero says the model
answered and got everything wrong. And the verdict is rebuilt and written after every single
task with `progress.complete` saying whether the run finished, because a model arm costs
minutes a task and a run killed halfway would otherwise leave nothing on disk at all.

The verdict is in `bench/verdicts/code.json`, written complete at
2026-09-18T13:27:17.017Z on node v24.15.0 from the command `node bench/code.mjs`, and it
does not say what this board was built to hear. Over 40 tasks and 160 hidden cases the
organism, running its own candidates and repairing them for up to three rounds, solved
10 of 40 tasks fully, 25.00%; the same model asked once with the same spec and the same
visible examples, with no run and no repair, solved 12 of 40, 30.00%; and the null arm,
which opens no socket at all, solved 0 of 40, 0.00%, which is the floor the two model arms
are measured against and the only number in the table that came out where it was expected
to. The gap is 5.00 points and it points at ALONE, not at the organism: the printed
statement reads "alone won: 12/40 = 30.00% of tasks fully solved against organism 10/40 =
25.00%, a gap of 5.00 points. The 95% interval is 27.36 points wide on the winner and
26.01 on the runner up, and a gap this size at these rates needs 611 tasks per arm to
separate from zero." A 5.00 point gap inside intervals 26 and 27 points wide, needing 611
tasks per arm to separate from zero when 40 were run, is not a finding that the loop hurts;
it is one arm measured twice with different samples, and this run cannot tell the two model
arms apart at all. What it CAN tell apart is either model arm from the floor: 25.00% and
30.00% against 0.00% on an interval 8.76 points wide.

Three things in the rows are worth more than the headline. The organism spent 2.58 rounds a
task on average against the alone arm's 1, so it paid 39617.63 ms a task against 25858.83
and bought nothing measurable with the difference. Of its 10 solved tasks, 7 were solved on
the first round and 3 only after a repair round, so the loop did convert three failures into
passes and simply did not convert enough of them to show through the noise. And 0 of its
candidates passed every visible case and then failed a hidden one, which means the loop
never bought a visible pass with a hidden failure: when it stopped early it was right to
stop. The two model arms agreed on 8 tasks passed and 26 tasks failed, and disagreed on 6
(2 to the organism, 4 to alone), which is the shape of sampling noise and not of a better
method.

The honest reading of this run is that the loop is BUILT and the claim is UNPROVEN at n=40
against this model. The bench prints the sample size the claim would need and the number is
611 tasks per arm, which at 39617.63 ms a task is about 6.7 hours of organism arm alone, so
the next move is not a bigger run of the same thing. It is a task set where the repair round
has something to repair: the failing-case feedback only helps where a first candidate is
close, and on 26 of these 40 tasks neither arm ever produced a candidate that passed the
visible cases, so the repair round had nothing to work from. The parser kind, 0/6 on both
arms, is the clearest example.

## the bar file was not the bar, and the second run of it disagreed with the first (2026-09-18)

The review found bench/verdicts/code.json holding 3 of 40 tasks where a 40 task bar was
claimed, then watched a further instructed run shrink it again. Both readings were right and
the cause was one line of this bench: the verdict was rebuilt and written to
bench/verdicts/code.json after EVERY task, by every run, of every shape, so a 3 task smoke
and an --arms null check each overwrote the bar with themselves. A second cause sat in the
argument parser, which took any word starting with two dashes as a flag: `node bench/code.mjs
--help` parsed as {help: true}, fell through to the run, and spent the whole bench over the
file that holds the bar. The fix is that SHAPE DECIDES THE PATH. A finished run of the whole
fixture with all three arms writes bench/verdicts/code.json; anything narrower writes
bench/verdicts/code-partial.json and its verdict reads NARROW, never GREEN; a run still in
flight writes bench/verdicts/code.progress.json, and that landing is deleted when the bar
lands, so exactly one live record exists. Every file now carries isTheBar, wroteTo, shape and
notTheBarBecause, so a reader who picks up the wrong file is told so by the file. The parser
now holds an allowlist of 17 flags with their kinds: an unknown flag, a missing value or a
value of the wrong kind prints usage and exits 2 having run nothing, and --help is a known
flag that prints usage. Measured beside the controls they replace: node --test
test/code.test.mjs 20 pass 0 fail 1235.5382 ms (four new tests, among them that exactly one
of the four (complete, barShaped) cases resolves to code.json), node --test
test/act-llm.test.mjs 15 pass 0 fail 155.9677 ms, and a real narrow run left the bar file
byte for byte identical at md5 6af57aaab225472ce772c2a5f4664029 before and after.

Then the bar was re-run whole, because nothing on disk preserved the lost one, and it did not
reproduce. bench/verdicts/code.json now reads GREEN with all seven structural checks true,
40 of 40 tasks reached, model qwen3:1.7b up, 902104 ms: organism 16/40 = 40.00% of tasks
fully solved against alone 8/40 = 20.00%, a gap of 20.00 points favouring the loop, with a
95% interval 29.06 points wide on the winner and 24.26 on the runner up, needing 39 tasks per
arm to separate from zero, against null 0/40 = 0.00% on an 8.76 point interval; hidden cases
64/160, 35/160 and 0/160. THE WINNER CHANGED SIDES BETWEEN TWO RUNS OF THE SAME BENCH. The
run this replaces measured organism 10/40 = 25.00% and alone 12/40 = 30.00%, a 5.00 point gap
the other way, on the same fixture, the same seed, the same model and the same code. Organism
moved 15.00 points and alone moved 10.00 points between runs, so the run to run movement is
